# Review Diff

## Rules
1. **Source of Truth:** Review the actual unified Git diff provided. Do not rely on summary texts or PR descriptions.
2. **Scope Constraints:** Evaluate changes strictly against the declared implementation scope. Flag unrelated refactoring or "feature creep" as MEDIUM findings.
3. **No File Modification:** Identify problems and provide remedies; do not modify any files directly.

## Execution Context & Blind Spots
* **Untracked Files:** Standard `git diff` does not output brand-new untracked files. Cross-reference the diff with any provided `git status --porcelain` data. If an untracked file is implied but missing from the unified diff text, explicitly flag it as a visibility gap.
* **Noise Filtering:** Ignore structural changes in autogenerated lockfiles (e.g., `package-lock.json`, `poetry.lock`) unless a specific security vulnerability (like an outdated package) is visible.

## Checklist

### 1. Security & Compliance
* **Credentials:** Search for hardcoded API keys, bearer tokens, private keys, or passwords.
* **Data Privacy:** Ensure no Personally Identifiable Information (PII) or internal system architecture details are exposed in log statements (`console.log`, `print`, `logger.info`).

### 2. Architecture & Side Effects
* **Production Safety:** Look for accidental modifications to production manifests, CI/CD pipelines, DNS settings, or infrastructure-as-code files.
* **Side Effects:** Ensure code paths dealing with state mutation (e.g., database writes, payment processing, transactional emails) do not trigger multiple times unintentionally or fail silently.

### 3. Code Quality & Robustness
* **Error Paths:** Verify that `try/except` or `catch` blocks do not swallow exceptions without logging or rethrowing. Ensure resources (file descriptors, sockets) are safely closed.
* **Edge Cases:** Inspect boundary conditions (null pointers, empty arrays, division by zero, asynchronous race conditions).

### 4. Test Coverage & Verification
* **Test Synchronicity:** Every logic modification or new path should ideally be mirrored by a matching test case update. Flag missing unit/integration tests as a gap.

## Output Format

### Positive Highlights
*(Optional) Briefly call out exceptionally clean code, clever optimizations, or comprehensive test cases.*

### Findings
Classify findings strictly using: **BLOCKER**, **HIGH**, **MEDIUM**, or **LOW**.

For **every** finding found, output using this exact Markdown template:

#### [SEVERITY] - File: `path/to/file.ext` (Line X)
* **Problem:** Clear description of the issue.
* **Consequence:** What happens in production or during deployment if this is merged?
* **Remediation:** Provide a concrete, copy-pasteable code snippet showing the corrected implementation.

### Verdict
End the response with exactly one of these three words in bold:
* **PASS** (No issues found)
* **PASS WITH NON-BLOCKING FINDINGS** (Only LOW or MEDIUM findings present)
* **BLOCKED** (One or more HIGH or BLOCKER findings present)
